# yourFittingRoom: verifiable desktop release requirements

The target is a reviewed, signed, tested release for explicitly supported operating systems. We cannot truthfully guarantee malware-free operation on every device, a compromised OS, every GPU/driver or future third-party update. Do not label the prototype certified safe, claim notarization/audit work that has not happened, or ask ordinary users to disable protection.

No hosting, purchase, photo upload, external scanner submission, tester invitation or credential sharing is authorized by this plan. Work and tests remain local. Local Netlify build preparation and companion archive refresh are authorized separately; they do not authorize deployment or a Git push. Personal test photos are excluded from security reports; dependency advisory queries send only public package names and versions.

## Implemented locally in this iteration

- Inference and image decoding moved out of the HTTP broker into a supervised Mac App Sandbox process. No unrestricted fallback is allowed. Unsupported platforms and unavailable GPU profiles disable generation.
- Cancellation terminates the single supervised worker. Analysis has a 300-second safety deadline, generation a 600-second deadline, and a sampled 12 GB worker resident-memory ceiling. These are failure limits, not completion estimates or guarantees about total GPU/OS memory. Only one operation is allowed; JSON pipes have bounded frame/queue sizes. Worker files are limited to 64 MB per file, open descriptors are capped and child process creation is disabled.
- The worker watches its parent and exits if the broker dies. Session expiry, withdrawal and delete-all converge on owner-specific cleanup. Tokens are invalidated immediately; cleanup failures stay retryable and are never reported as success.
- The local workspace is a static build of the existing React UI, served only from verified, allowlisted files at `http://127.0.0.1:8765`. CSP permits local scripts with pinned inline hashes and same-origin API connections; it blocks remote scripts, workers and frames. The workspace accepts garment uploads; remote product importing is unavailable there. No person/result is returned to a hosted website.
- An internal Mac fixed-code bundle embeds the Python runtime, dependencies, verified source and local UI. It uses this machine's verified model-data link and ad-hoc worker signing: it is not a portable installer or public download.
- The source and refreshed Windows ZIP have an opt-in AppContainer/Job Object worker candidate, explicit NVIDIA CUDA / AMD ROCm / Intel XPU / CPU profiles, separate backend environments, numerical/operator probes and `Test Windows.cmd`. CUDA/CPU candidates allow Windows 10 2004+ and 11 x64; AMD/Intel GPU candidates require Windows 11 with supported hardware/drivers. No unrestricted or automatic CPU fallback is used. All profiles remain unexecuted on real Windows. AMD's small source bootstrap is pinned and verified before a development-only local build. Full dependency locks, real hardware quality/performance/isolation tests and signed installers remain pending. Details: [WINDOWS_TESTING.md](WINDOWS_TESTING.md).
- AMD's pinned Torch wheel requires an older setuptools with a source-distribution exclusion advisory. The development-only exception is confined to its separate hash-pinned environment and verified local wheel builds, with no source-distribution publishing or personal build inputs. Other profiles retain the newer toolchain. Resolve/review this dependency exception before public release; details and upstream advisory are in [SECURITY.md](SECURITY.md). Setup now rejects unexpected `pip check` conflicts rather than upgrading into incompatible dependencies.

Remaining release work: sandbox the broker/native file-selection boundary; replace temporary path exceptions with reviewed portable entitlements; implement/test Windows isolation; build portable model storage and repair/uninstall controls; complete licence/SBOM review; sign/notarize final installers; add signed updates; obtain independent review and scan evidence; test clean machines and the exact downloaded artifacts. Do not ask ordinary users to approve development launchers as a substitute for these gates.

## Current technical hardening

- Only the current local web origins may pair; the withdrawn hosted origin is rejected.
- Mac and Windows source downloads share a fixed SHA-256 check and bounded extraction that rejects traversal, links and special files. Existing source is compared with the verified archive; modified or additional imported Python modules stop setup/startup.
- Main try-on/pose/parser weights and prepared recognition model/config/tokenizer files are checked before native startup. Current recognition artifacts are hashed from the reviewed local build; hashing is an integrity control, not an independent safety verdict.
- Registry installs use explicit official indexes and binary wheels. The Mac dependency and pip bootstrap locks have hashes enforced by pip. Windows remains a pinned experimental profile until its complete platform dependency lock is independently resolved/tested. Source-download setup still builds FASHN on the user device and remains development-only. The internal fixed-code bundle avoids that step but is not portable or notarized.
- No quarantine removal, OS approval automation, antivirus disabling, elevation or publishing is performed.

## Execution order

1. Finish the dependency/SBOM/build review and prepare an unsigned fixed-content installer for internal validation on Mac and Windows. Do not distribute it as production-safe.
2. Implement and test platform isolation plus consent/IPC and uninstall behaviour. Validate hardware, identity/garment quality, resource use and data deletion on clean machines.
3. Obtain legitimate signing credentials through owner-controlled accounts. Keep private keys out of chat, archives and source control. Account enrolment, paid certificates/services and external submissions need separate explicit authorization.
4. Independently review and scan the final artifacts. Sign/notarize, then test those exact downloads with OS protection enabled. Re-run checks for every release.
5. Invite testers or publish only after a new explicit instruction and the release evidence is complete. No publication is authorized now.

A defensible eventual statement is: “This version is signed, has passed the listed security checks on these supported systems, processes selected photos locally, and has no known unresolved findings as of this date.” Only use it when the evidence actually exists. Never substitute “guaranteed malware-free for any system.”

## Local category and garment-detail work — 15 October 2026

The project now has a shared category catalog for native tops, bottoms and one-piece routing: tops/shirts/T-shirts/sweaters/hoodies/jackets; pants/jeans/shorts/skirts; dresses/jumpsuits. Expanded categories remain experimental pending per-category photos and output review. Unsupported items fail closed. The person photo needs lower-body coverage for bottoms/one-pieces. Automatic garment analysis offers editable category, clothing-range and visual fabric cues, with uncertain cases left for confirmation; composition/physical fit are not inferred.

The user explicitly selects the wearer profile. No person-image gender inference is implemented or claimed. Missing declarations and mismatched Women/Men clothing/profile pairs are rejected in both the browser service and the local API before inference; confirmed unisex clothing allows either profile. These checks cannot verify whether the selected profile reflects the person pictured.

Balanced generation uses 30 model steps and Fast uses 20. The actual public-fixture 30-step run completed in 165.98 seconds at 576 × 864; subsequent result deletion stopped the worker and health reported no loaded worker. One inspected output transferred the shirt coherently; this is not proof of photorealistic fabric or expanded-category quality. Release gates for hardware, security, signing and Windows remain. No archives were regenerated or deployed for these changes.
