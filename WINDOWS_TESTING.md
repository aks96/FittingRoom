# Windows worker: internal test candidate

The project and refreshed Windows ZIP contain a Windows AppContainer worker, NVIDIA/AMD/Intel/CPU compute profiles and a Windows validation runner. They have **not been executed on Windows**. Mac tests verify contracts and regressions, not Windows isolation, GPU compatibility, image quality or speed. This is an internal test candidate, not universal Windows support. No deployment is performed by building the download.

## First test target

- Standard user account and **64-bit Python 3.12**, installed per-user from python.org. No administrator rights, firewall exceptions or security-policy changes are requested. Windows ARM, 32-bit Windows, older Windows and mobile generation are unsupported.
- At least 16 GB system RAM is the testing target, not a compatibility guarantee. Available RAM, dedicated GPU VRAM and shared graphics memory are different. A recent computer or an Intel/AMD **processor** does not identify its GPU. The setup launcher displays adapter vendor/name/driver when available; it does not change drivers or send the inventory anywhere.

| Setup option | Candidate OS | Pinned compute stack | Limit |
| --- | --- | --- | --- |
| NVIDIA CUDA | Windows 10 2004+ / 11 x64 | Torch 2.13.0 / torchvision 0.28.0, CUDA 12.6 index | Compatible NVIDIA GPU/driver; newer GPU generations may need another reviewed profile. |
| AMD ROCm | Windows 11 x64 | Torch 2.12.0 / torchvision 0.27.0, ROCm 7.14.0 | Selected supported Radeon/Ryzen GPUs and matching vendor driver. Available kernel packages do not establish vendor support or app compatibility. |
| Intel XPU | Windows 11 x64 | Torch 2.13.0 / torchvision 0.28.0, XPU index | Supported Arc/Core Ultra graphics and matching driver; not all Intel UHD/Iris GPUs. |
| CPU | Windows 10 2004+ / 11 x64 | Torch 2.13.0 / torchvision 0.28.0, CPU index | Explicit Intel/AMD CPU testing. Can be impractically slow or hit the generation deadline; no successful-image guarantee. |

Actual numerical/operator checks must pass **inside AppContainer** before image processing. GPU unavailability never silently selects CPU or a cloud service. A driver may work outside AppContainer yet fail inside it; the worker stays disabled in that case.

Several GB of disk space/downloads are needed. Each backend has a separate `.runtime/windows-venvs/<profile>` environment while model files are shared. Switching backends reuses models and preserves other profiles; stop the companion first. AMD's default `all` target installs multiple kernel packages and can use substantially more storage/bandwidth. Setup verifies a small, SHA-256-pinned AMD source bootstrap before building it with the installed build tools and no automatic build isolation/dependency download. Other compute/dependency installs use binary wheels; the existing separately verified FASHN source build remains. A complete per-platform dependency hash lock and fixed-content installer remain unfinished.

AMD's Torch build also needs an older setuptools than the other profiles. Its separate environment uses a hash-pinned compatible version with a documented source-distribution advisory; the app builds only verified local wheels and publishes no source distributions. See the scoped development exception in [SECURITY.md](SECURITY.md). Do not treat this as a production-approved dependency profile. Setup checks dependency consistency and refuses unexpected conflicts.

## Test the extracted Windows ZIP

Extract the complete `yourFittingRoom-companion-windows.zip` with Windows **Extract All**. Keep its folder together. It contains the fixed `workspace` UI, source, requirements, `Set up.cmd`, `Test Windows.cmd`, `Start AI.cmd` and this guide. It does not contain Python, installed environments, models, credentials or personal photos. Use the launchers at the extracted folder's root and follow steps 2–6 below. The `.runtime` directory is created by setup on that Windows device; never copy a Mac environment there.

## Test from updated project source

1. Copy the updated project source to a folder you own on Windows. Include `local_ai`, `security`, and `scripts/companion`. For the fitting-room UI, also include **only** the existing `.runtime/local-workspace` static export from this project at that same relative path, or the equivalent reviewed `workspace` folder. Do not copy the Mac Python environment, Mac executables, credentials, personal photos or other `.runtime` contents. There is no need to install Node for this bundled UI.
2. Open `scripts/companion/Set up.cmd`. Review detected adapters, then select NVIDIA CUDA, AMD ROCm, Intel XPU or explicit slow CPU testing. This installs into the matching Windows runtime folder, checks numerical operations on the selected device and only then downloads verified model data. OS protections stay enabled. If it fails, keep the error; do not bypass verification or run as administrator to force it.
3. Close any running companion, then open `scripts/companion/Test Windows.cmd`. It runs isolation, lifecycle and configured compute/model-access checks. Review `.runtime/windows-validation/report.json`. A failure keeps the candidate unapproved; no personal images are used. The report contains OS/runtime/GPU/driver metadata, a worker-source digest and check outcomes, not account names, hardware serials, pairing codes or selected photos. Console errors may contain local paths; redact those before sharing.
4. If the checks pass, open `scripts/companion/Start AI.cmd` and explicitly choose experimental testing. Every worker creation repeats the real OS-denial and compute probes. Open **http://127.0.0.1:8765**, pair privately and consent. The broker never falls back to unrestricted processing or a cloud API.
5. First use the public upstream fixtures downloaded by setup: `.runtime/fashn-src/examples/data/model.webp` and `garment.webp`. Confirm the detected garment details/photo type, select the wearer profile yourself and generate a preview. Record actual elapsed time and visually inspect face/body preservation, garment colour, logos and texture. A passing operator probe does **not** establish that the full model fits in GPU memory or produces acceptable images.
6. Test Cancel, Disconnect, deletion, expiry and a closed companion. Check that previews are purged and its worker exits in Task Manager. Windows releases the terminated process's committed memory/GPU allocations; model files stay on disk for reuse. OS swap/diagnostics are outside app control, and no forensic-erasure guarantee is made.

The launchers work both in `scripts/companion` in the project and at the root of the refreshed companion source archive. Verify the ZIP checksum against the download page or `checksums.txt`; an old ZIP does not acquire the new worker automatically.

For developer tests with a known AMD architecture, `py -3.12 local_ai\windows_setup.py --compute rocm --amd-target gfx1100` downloads only that target's kernel package. Use the correct vendor-documented target for your GPU; the setup probe checks the actual architecture. An explicit `--device-index 1` selects a second GPU within that backend, not the Windows Task Manager GPU number. Invalid indices and wrong Torch vendor builds are rejected. The default AMD setup discovers and records the actual runtime target so the isolated worker need not launch a hardware-discovery child process.

## What the runner checks

- The actual worker token is the expected AppContainer identity with no capabilities, and the process belongs to a Job Object.
- Unrelated disposable-file reads/writes, code/model writes, loopback/Internet connection attempts and child-process launches are denied. Cache writes and approved model reads work. Network timeouts/refused connections do not count as a successful denial.
- Matmul, attention, normalisation, embeddings, convolution, random tensors and rotary calculations run on the selected device. Numerical outputs are checked against CPU references. Intel/AMD use FP16 diffusion and FP32 rotary math; parsing/pose/garment recognition stay on CPU. Their attention computes query slices against the complete key/value sequence to bound temporary memory if fused kernels are missing. This preserves the computation but can reduce throughput. No reduced-resolution or fabricated preview is substituted.
- Only three anonymous pipe handles are inherited. A suspended process is assigned to a one-process, 12 GB committed-memory Job before it can execute. Cancellation kills the Job. Closing/crashing the broker closes the only Job handle and kills the worker. GPU VRAM is **not** capped by this memory limit.
- Separate disposable tests cover cancellation, worker crash, a small 256 MB memory cap, broker death and recovery cleanup. No real photo is required for these tests. Passing the runner never sets `releaseApproved` or `generationTested` to true.

The runtime temporarily grants its private AppContainer SID read access to approved Python/code/source/model directories and write access to its own low-integrity cache. It does not grant access to your home folder or photo paths. Normal cleanup removes its SID's ACL entries and profile/cache while preserving other permissions. A broker crash kills its worker, but narrow ACL/profile/cache remnants can remain until the next startup/cleanup. Python installed in an administrator-owned directory can make these grants fail; use a per-user installation rather than elevation. The broker/setup still have ordinary user permissions. Aggregate disk quotas, a signed installer, trusted updates, full dependency validation, independent security review and clean-machine tests remain release gates.
